# Online commerce policy

Phase 2A passed before Phase 2B implementation began. Products, variants, prices, promotions, inventory, customers, sales, returns and journals retain their existing canonical services.

Order placement reserves quantities and records a server quote; it creates no physical movement, revenue, COGS or payment. Cart browsing never reserves. Public orders use bounded reservations, with expiry included directly in availability queries; no background worker is assumed. POS and reservations acquire the same sorted transaction-scoped SKU/location locks before checking availability.

Fulfillment locks the order and runs hold, canonical checkout, reservation consumption and order linking in one database transaction. Failed actions roll back together. Retries return the original sale. Prices/promotions are revalidated; a changed total requires the customer's acceptance before fulfillment. Serial numbers are selected by staff at fulfillment and recorded through the canonical serial service.

Cash on collection/delivery is recorded only when staff confirm collection. Manual bank/QR payments require a staff verification reference. A public claim of payment never marks an order paid. There is no bank or gateway integration. Delivery uses the existing billing helper's separate delivery-fee convention; it is not discounted or taxed by merchandise rules. Completed delivery fees are not automatically refunded by a merchandise return. Returns and staff-assisted exchanges use the original canonical sale.

Guests are not merged into existing customers by name, phone or email. Guest order access requires an opaque browser secret. Customer accounts are linked only through a staff-issued, single-use activation code following the merchant's identity check. Passwords and sessions are hashed; browser session cookies are HttpOnly and SameSite. Guest loyalty/store-credit redemption and public credit sales are disabled. Customer-linked loyalty earnings use the existing sale/return services. Online balance redemption remains disabled by default.

Public APIs under `/api/storefront/*` explicitly select safe fields, cap request size and pagination, reject cross-origin mutations, rate-limit in PostgreSQL and disable caching for prices, availability, quotes, accounts and orders. The legacy `/api/store/orders` remains staff-only. No admin API is made public. Notification lifecycle events are retained for future delivery integration; no message is described as sent without a provider.

The canonical price channel values remain `retail_pos` (IN_STORE) and `online` (ONLINE). Customer-group pricing comes from the authenticated account's canonical customer ID, never a customer ID or group supplied by a public client. Public pricing exposes the payable amount and a generic label, not internal rule IDs or margin data. Placement requires a server quote fingerprint; a changed quote must be acknowledged again. The owner can explicitly accept a revised quote before fulfillment. Idempotent retries return the original order or sale.

Public reservations default to 120 minutes, with merchant configuration bounded to 15–1,440 minutes. Expired reservations immediately stop reducing availability, even without a cleanup worker. Expired orders cannot be fulfilled. Cancellation is nonfinancial and releases reservations. A cancelled manual-payment order records that payment review may be needed; it does not claim to have refunded a bank transfer. Refunds and exchanges require the linked canonical sale and authorized staff action.

Manual QR/bank payment stays PENDING until staff verify receipt and provide a reference during fulfillment. Verification has a separate permission from order fulfillment; it is denied to the default cashier role. Offline payment intents describe provider, amount, currency, reference, instructions and next step, and explicitly declare that automatic confirmation/refund is unavailable. There are no gateway callbacks or simulated refunds.

The public catalog paginates 24 products and product detail paginates 100 variants, supporting up to 1,000 variants across ten pages. Six merchant-enabled attribute facets expose at most 40 values each. Price sorting/ranges and availability filtering apply to the displayed representative SKU and require narrowing to at most 1,000 matching products. The UI labels this as the shown option; it does not imply every variant has the displayed price or stock.

Published local product media is resized to bounded WebP widths through `/api/storefront/image`; arbitrary remote fetches are prohibited. Merchant-provided HTTPS images remain external originals. Prices, stock and private customer data are never served through that image cache. Uploaded receipts are no longer mirrored into the public directory. Next routes legacy `/uploads/receipts/*` through authenticated media access. A deployment that serves the filesystem directly through Apache, nginx or a CDN must also deny direct receipt paths; application routing cannot protect an independently exposed static directory.

Deployment must set `NEXT_PUBLIC_SITE_URL` to the actual HTTPS origin when terminating TLS at a proxy, use the normal secure-cookie production configuration, and verify the real proxy/CDN, upload directory and edge abuse controls. Local PostgreSQL rate limits are active; production network controls and external payment delivery were not exercised by the local acceptance gate. Public balance redemption is disabled for all accounts in this phase; authenticated customers can see canonical balance histories and earn through canonical completed sales where configured.
